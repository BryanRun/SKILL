# 14 · 中间件平台化设计共识（P2/P3 软规则）

> **来源依据**：中间件平台化策略与落地框架 + 中间件平台能力规划（团队内部权威输出）
> **定级原则**：本维度规则**全部为 P2 / P3**，属"值得改 / 可选改进"性质，不阻断合入。
> 命中后必须以 inline comment 形式提示，但**不**强制 -1。

---

## 一、平台化设计总目标（评审时的"价值轴"）

代码评审在判断"该不该这么写"时，应主动对齐以下平台化总目标。任何明显**违背总目标**的写法都应至少给 P3 提示：

| # | 总目标 | 反向信号（需在 review 中提示） |
|---|---|---|
| G1 | 从"项目驱动、各自交付"转向"平台沉淀、项目复用" | 改动只解决单项目场景、对其他项目无适配规划 |
| G2 | 一套代码适配多项目、多芯片平台 | 通过"if 项目名 / if 芯片型号"分支硬编码差异 |
| G3 | 通过配置化 / 插件化覆盖差异需求 | 差异通过新增 class / 新增分支堆叠，而非走配置或扩展点 |
| G4 | 接口统一、可演进 | 改动直接修改公共接口签名却没有版本/兼容策略 |
| G5 | 平台基线统一验证、质量一致 | 同一 bug 在多个项目分支重复修，未沉淀回平台层 |

---

## 二、需求三分类模型（评审时的"配置化判定法"）

| 分类 | 标识 | 平台化处理原则 |
|---|---|---|
| **通用需求** | 🟢 | 所有项目共性 → 平台基线**必须覆盖**，不应额外配置开关 |
| **可选需求** | 🟡 | 部分项目有 → **必须**通过配置开关控制，且开关默认值偏向"关" |
| **定制需求** | 🔴 | 客户独有 → **必须**通过插件 / 扩展点接入，**禁止**进入平台主干 |

> **评审应用**：看到一段差异化代码时，先判断它是 🟢 / 🟡 / 🔴；如果归为 🟡 但没走配置，或归为 🔴 却写在平台主干，应提 P2 / P3。

---

## 三、配置化三层模型（评审"配置项"的判定标准）

| 层级 | 时机 | 典型形式 | 评审关注点 |
|---|---|---|---|
| **静态配置** | 编译期 | feature flag / overlay / 编译宏裁剪 | 命名规范、宏作用域、未启用时是否可裁掉 |
| **动态配置** | 运行时 | 接入统一配置化框架 | 默认值、热更新行为、读取一致性 |
| **客户配置** | 部署/烧录 | 客户可自定义参数范围与约束 | 边界检查、非法值兜底 |

新增任何配置项都应在 commit message / 设计说明中明确**层级 + 默认值 + 生效粒度（项目 / 客户 / 用户）**，否则给 P2-PLAT-5。

---

## 四、平台 / 项目 / 客户三层分离（架构层评审）

```
┌─────────────────────────────────────────┐
│  customer 层  ← 客户定制（插件 / 扩展点） │
├─────────────────────────────────────────┤
│  project 层   ← 项目差异（配置化 / 适配层）│
├─────────────────────────────────────────┤
│  platform 层  ← 通用代码（平台基线）      │
└─────────────────────────────────────────┘
```

- **下层不感知上层**：platform 层不应引入 project / customer 的特化逻辑
- **上层不修改下层**：project / customer 层不应直接修改 platform 层接口签名
- **跨层调用单向**：上层调下层走稳定接口；下层回调上层走扩展点

## 五、ISO 25010 八大质量属性（评审"方案合理性"的标尺）

| 属性 | 评审应关注 |
|---|---|
| 功能适合性 | 功能完整、覆盖差异 |
| 性能效率 | 时延、资源占用、启动速度 |
| 兼容性 | 跨芯片平台（8155 / 8255 / 8775 / 8797 等）适配成本 |
| 可用性 | 故障恢复、降级策略 |
| 可靠性 | 稳定性数据（ANR / Crash / 异常率） |
| 安全性 | 信息安全 / 功能安全合规差异 |
| 可维护性 | 代码复用率、改动影响面 |
| 可移植性 | OS / 芯片平台切换成本 |

> **评审应用**：对中等以上 CR（>= 100 行 / 跨多模块），如方案文档 / commit message 完全没有提及上述任何一项，给 P3-PLAT-7。

## 六、底座能力复用清单（避免重复造）

中间件平台已有/规划的统一底座能力，业务模块**禁止**重复实现：

| 底座能力 | 统一组件 | 评审反向信号 |
|---|---|---|
| 跨进程通信 | ALC / FDBus / SOMEIP（按链路选） | 自己起一套 socket / pipe / shm |
| 持久化存储 | PSIS（统一存储服务） | 自己封 SharedPreferences / 文件读写做持久化 |
| 健康管理 | WatchDog / 心跳 / PHM 统一框架 | 自己起 daemon thread 做存活检测 |
| 启动管理 | 进程启动 / 停止 / 恢复统一服务 | 自己 fork / shell 拉起子进程 |
| 配置框架 | 静态/动态/客户三层统一模型 | 自己 init 阶段读配置 + 自定义 reload |
| 时间管理 | TimeMng（同步 / 闹钟 / 倒计时） | 自己用 AlarmManager 做关键定时唤醒 |
| 日志 | 统一日志组件（采集 / 打包 / 上传） | 自己另起一套 file rotation |

命中以上情况 → P2-PLAT-4（重复造底座）。

## 七、平台化设计共识 — 评审检查项（rule_check_table 用）

> 全部规则 P2 或 P3，命中后写 inline 提示，**不**作为 -1 依据。

| 规则 ID | 级别 | 名称 | 触发条件 |
|---|---|---|---|
| **PLAT-1** | P2 | 硬编码项目差异 | 代码出现 `if ProductName.equals("XXX")` / `#ifdef PROJ_XXX` 直接区分项目，且差异属"可选需求"性质 |
| **PLAT-2** | P2 | 平台层引入项目/客户特化 | 文件路径在 platform / framework / common 等公共层，但实现里写死了项目/客户专属逻辑 |
| **PLAT-3** | P2 | 公共接口违反治理规范 | 修改公共 AIDL/HIDL/IDL 接口（删字段、改签名、改语义）但 commit message 无版本/兼容策略说明 |
| **PLAT-4** | P2 | 重复造底座能力 | 自实现通信 / 持久化 / 健康管理 / 启动 / 配置 / 时间 / 日志 等已有统一组件覆盖的能力 |
| **PLAT-5** | P2 | 配置项无层级声明 | 新增配置项但无明确"静态/动态/客户"层级标识，或缺默认值 |
| **PLAT-6** | P3 | 可选需求未走配置化 | 🟡 类需求被实现为 if/switch 分支而非接入配置框架 |
| **PLAT-7** | P3 | 缺质量属性设计说明 | 中大型 CR（≥ 100 行 / 跨模块）的 commit message 未提及任何 ISO 25010 维度（性能 / 兼容 / 可移植 等） |
| **PLAT-8** | P3 | 增量功能未对齐平台基线 | 同类能力已在平台基线规划中，但 CR 选择在项目分支单独实现，未声明回流计划 |

## 八、评审输出格式

每条平台化命中按下列格式：

```
[P<级>][PLAT-<n>] <file>:<line> - <一句话标题>

**依据**：14-platform-design-principles.md §<对应章节>
**现象**：<具体代码片段 + 命中的反向信号>
**原理**：<为什么违反平台化共识>
**建议**：<对齐平台化的具体改法（如改走配置化 / 走扩展点 / 复用底座）>

**示例**：
// Before
<当前写法>
// After
<平台化对齐写法>
```

## 九、与其他维度的边界

| 场景 | 归属维度 |
|---|---|
| 接口签名破坏向后兼容 | **04 错误处理 + 边界**（契约破坏 P0） + 14（接口治理 P2） |
| 重复造的底座能力同时引入并发 bug | **09/11/12 并发专项**（按语言 P0/P1） + 14（重复造底座 P2） |
| 重复造底座引入隐私数据持久化 | **10 隐私合规**（P0 三重门控） + 14（P2） |
| 配置项缺默认值导致 NPE | **04 错误处理**（P0/P1） + 14（P2-PLAT-5） |

> 平台化维度**叠加**而非**替代**其他维度。其他维度命中 P0/P1，按其他维度给分；本维度仅追加平台化角度的 inline 提示。

## 十、不评/豁免清单

以下场景**不**触发本维度规则：

1. CR 明确标注 `[hotfix]` / `[临时方案]` 且 commit message 已说明回流时机
2. 项目分支专属仓库（如 `*_baic_*` / `*_chery-kp31_*` 路径）做客户专属适配
3. 测试代码 / 示例代码 / 工具脚本
4. 改动行数 < 30 且仅修复单点 bug 的小 CR

---

## 十一、复盘与演进

平台化规则每季度复盘一次：

- 新增统一底座能力 → 更新 §六 表格
- 新增配置化模式 → 更新 §三 模型
- 新增反向信号案例 → 在对应规则后追加"案例"小节
